Why Printer Security Visibility Matters

Network printers sit on trusted VLANs with opaque configurations.

Printers and MFPs speak SNMP, IPP, raw TCP 9100, and vendor-specific HTTP dialects, hold TLS certificates, and store network credentials—yet most infrastructure tools treat them as unmonitored black boxes.

Silent protocol exposure

× High risk

Printers frequently ship with SNMPv1/v2c community strings enabled, plain-HTTP admin consoles, self-signed or expiring TLS certificates, and unauthenticated raw port 9100 open across office subnets.

PrintMarshal probes TCP ports (21, 23, 80, 443, 515, 631, 9100), inspects TLS handshakes on 443/631, and reads live protocol state.

The "unknown = pass" trap

? Evidence gap

Standard Printer-MIB and IPP attributes do not expose every security control on every vendor model. Dashboards that collapse unreadable settings into "0 issues" create false compliance confidence.

PrintMarshal keeps pass, fail, and unknown separate in every assessment and in the 126-family device catalog.

Unverified configuration writes

⚠ Drift risk

Printer firmware often returns OK to an SNMP SET or IPP Set-Printer-Attributes request while silently ignoring or truncating the value.

PrintMarshal runs a dry-run diff first, captures rollback values, re-reads every written key, and labels outcomes verified, diverged, or unverifiable.
Guided Product Walkthrough

From fleet discovery to verified configuration changes.

Every screen below is captured directly from the shipped PrintMarshal web console running against the built-in printer simulator (cmd/pm-sim). Select any step to inspect the workflow, or click a screenshot to enlarge.

Step 01 · Fleet Inventory

Discover & reconcile printers across protocols

Scan target CIDRs, IP ranges, or single hosts via SNMP (v1/v2c/v3), IPP/IPPS, and TCP port probes, or listen passively with mDNS, SSDP, and WS-Discovery.

  • Deterministic deduplication: Reconciles observations by serial → UUID → MAC → IP address so multi-homed or DHCP-reassigned printers never duplicate.
  • Live operational telemetry: Polls CMYK/mono supply bars, lifetime page counters, input/output tray state, and Printer-MIB alerts.
  • Table & mobile card views: Switch between high-density fleet tables on desktop and supply-focused device cards on mobile.
Boundary: Discovery and polling are strictly read-only. Operator-set display names, locations, asset tags, and notes are never overwritten by device polls.
Step 02 · Policy Assessment

Identify failed and unknown security checks

Run the built-in 14-item Baseline policy—or build custom policies from the 17-item security catalog—against individual devices or groups.

  • Pass / Fail / Unknown breakdown: Every policy item shows its severity (Critical, High, Medium, Low), pass rate bar, failing device count, and unknown count.
  • Management-path awareness: Highlights items that could sever SNMP or HTTP connectivity if remediated without an alternative path.
  • Assess-only vs remediable rules: Clearly labels which items are Assess-only (such as Administrator password set or Raw port 9100) versus driver-remediable.
Boundary: Automated policy remediation requires a driver implementing SecurityWriter (CapWriteSecurity). Standards SNMP/IPP drivers do not write security settings.
Step 03 · Device Security Detail

Inspect a device and its supporting observations

Drill into any printer's Security tab to see the exact observed values behind its compliance score alongside its TLS and certificate inventory.

  • Transparent scoring math: On fin-laser-4200dn, 4 / 5 readable items pass (weighted score 81.8), while SNMP v1/v2c enabled fails (is true, want eq false).
  • Explicit unknown listing: All 9 unknown items are named directly on the card with the explanation: "not readable on this device; counted but not scored."
  • Certificate & TLS probe view: Displays certificates reported by a driver, observed via TLS handshake on ports 443/631, or issued by PrintMarshal through SCEP, EST, or ACME.
Boundary: PrintMarshal can enroll certificates with SCEP, EST, or ACME DNS-01, but installing an issued certificate onto a printer requires a CertManager driver.
Step 04 · Support & Evidence

Understand available capabilities and next actions

Every device detail page pairs live driver capabilities with the Support & evidence card so operators know what works on that specific printer before attempting changes.

  • Catalog match confidence: Matches device make, model, sysDescr, and enterpriseId against 126 researched enterprise families (here, an Exact match to Ricoh RI02 · IM C3010).
  • Documented vs Observed vs Unknown: Compares what primary vendor documentation describes (documented) against what PrintMarshal drivers actually answered on the live device (observed · snmp, ipp).
  • Operator qualification control: Every catalog family ships as Research candidate (unvalidated) until an operator records lab validation or a field note.
Boundary: Research catalog coverage is documentation context, not validated driver support. Operations depend on the capabilities observed on the device.
Step 05 · Dry-Run Preview & Verification

Preview a supported configuration change and inspect its result

Applying a configuration profile runs a live read-only preview first, shows exact per-setting diffs, captures rollback values, and verifies every write by reading the device back.

  • Dry-run preview by default: Applying Standard Office Fleet Baseline to fin-laser-4200dn shows 2 settings that Would write (Organization, Default duplex) and 2 settings that already match.
  • Read-back verification: After a real apply, PrintMarshal re-reads the modified keys and records verified (device reports the new value), diverged (device reports a different value), or unverifiable.
  • One-click revert flow: Every real write stores previous values so operators can preview and revert changes from the device's Write history card.
Boundary: Standards drivers write a bounded set of SNMP Printer-MIB/MIB-II and IPP Set-Printer-Attributes keys. No vendor-private ConfigWriter ships today.

Core Capabilities

One console for fleet discovery, security posture, and controlled configuration.

PrintMarshal separates read-only observation from state-changing operations, keeping driver boundaries and verification outcomes visible at every step.

✓ Implemented ◐ Device-dependent depth

1. Discover the fleet & monitor live health

Combine active CIDR/range scans (SNMPv1/v2c/v3, IPP/IPPS, eSCL, TCP port probes) with zero-configuration listeners (mDNS/Bonjour, WS-Discovery, SSDP) and live SNMPv1/v2c trap ingestion.

Reconciliation
Matches serial → UUID → MAC → IP so printers keep their history, groups, and audit trail when IPs change.
Health & consumables
Tracks toner/drum/waste levels, 14-day burn-rate forecasts, stock rooms, and lifetime page counters (total, mono, color).
Operator metadata
Display name, location, asset tag, and notes are stored in operator-owned fields that device polling never overwrites.
✓ Assessment & Enrollment Implemented ⬚ Remediation & Install require driver

2. Understand security posture & certificate lifecycle

Evaluate printers against the 14-item Baseline policy or custom rules spanning legacy protocols (SNMPv1/v2c, Telnet, FTP, Raw 9100, WSD/SLP/LLMNR), TLS versions, admin password state, and certificate validity.

Evidence integrity
Unreadable settings evaluate to unknown and are excluded from the compliance score denominator rather than assumed compliant.
CA enrollment
Issue device certificates via SCEP, EST, or ACME DNS-01 (manual TXT challenge). Private keys are encrypted at rest and never downloadable via the API.
Shipped boundaries
Installing an enrolled certificate onto a printer requires a CertManager driver, and remediating security settings requires a SecurityWriter driver. No real-vendor CertManager or SecurityWriter ships today.
✓ Dry-run & Read-back Implemented ◐ Writable keys depend on driver

3. Review supported configuration changes & verify outcomes

Read device settings into versioned snapshots (up to 50 per printer), compare any two printers side-by-side, track drift against reusable profiles, and preview every change before writing.

Standards write scope
Standards snmp writes sysName, sysLocation, sysContact, prtGeneralPrinterName, default input tray, and marker index. Standards ipp writes location, info, organization, organizational unit, and *-default print attributes when the printer supports Set-Printer-Attributes.
Read-back proof
Every applied setting is re-read from the device and recorded as verified, diverged (accepted write but reports a different value), or unverifiable.
Rollback history
Previous values are saved automatically with each write record so operators can run a dry-run revert from the device's Write history card.
Device Coverage & Implementation Status

Clear boundaries between what ships today, what depends on device support, and what requires a driver.

PrintMarshal never presents a research catalog entry as a validated driver, or an accepted write as a guaranteed change. Every capability is labeled by its actual implementation status in the repository.

Self-Hosting & Platform Security Architecture

Built for internal network operations—with strict credential and write controls.

Whereas printer security assessment inspects your fleet, PrintMarshal's security architecture governs how the server itself stores secrets, authenticates operators, and gates network traffic.

Purpose-bound credentialsAES-256-GCM

SNMP communities, SNMPv3 auth/priv keys, HTTP credentials, CA secrets, and enrolled private keys are encrypted at rest with AES-256-GCM using PM_SECRET_KEY.

Every credential declares a purpose—read, write, or both. Read-only credentials are rejected by write workflows, and secrets are never returned in API responses or logs.

RBAC, OIDC & CSRF defense3 Roles

Supports local bcrypt accounts, OIDC (Authorization Code + PKCE), LDAP bind authentication, and SHA-256 hashed pmk_… API tokens across admin, operator, and viewer roles.

Cookie-authenticated state changes enforce Sec-Fetch-Site and Origin validation. Group-scoped API tokens restrict device/group mutations (not a multi-tenant isolation boundary).

Single-binary deploymentSingle active node

Ships as one Go binary with the React UI embedded and an embedded SQLite (WAL) database—or connects to PostgreSQL for external storage.

Run a single active server process per database; scheduler and job workers run in-process without distributed locking. Explore full details on the Security page.
