Technical FAQ

Direct answers on protocol scope and boundaries.

How PrintMarshal interacts with network printers, evaluates security compliance, handles configuration changes, and defines the scope of its optional add-ons.

1. Does discovery or polling ever write to my printers?

No. Active CIDR/IP discovery, passive multicast listeners (mDNS / DNS-SD and WS-Discovery), and scheduled background polling are strictly read-only. They issue SNMP GET / GETNEXT / GETBULK requests and IPP Get-Printer-Attributes queries.

PrintMarshal only sends write commands when an authenticated admin or operator explicitly triggers a configuration apply, security remediation, credential rotation, certificate install, or simulator firmware job.

2. Which printer brands and models work today?

Any network printer that implements standard SNMP v1/v2c/v3 (RFC 1213 MIB-II, RFC 2790 Host-Resources-MIB, RFC 3805 Printer-MIB) or IPP / IPPS works out of the box for discovery, supply/tray/counter monitoring, alert collection, and port/TLS security probing.

PrintMarshal also ships an enterprise research catalog covering 15 brands, 126 model families, and 495 base model identifiers. The catalog explicitly marks 0 physically validated out of the box until an operator records lab qualification (PUT /api/catalog/qualifications/{familyId}), keeping vendor documentation separate from live device observations.

3. Why do some Baseline security policy checks show Unknown?

PrintMarshal's canonical settings catalog defines 84 setting keys across 10 areas (internal/model/settings_catalog.go), including 43 security-tagged keys. Standard SNMP and IPP expose protocol reachability, SNMPv1/v2c state, IPPS support, and TLS certificates, but do not standardize vendor-specific settings like security.adminPasswordSet or protocols.https.redirectFromHttp.

When no driver reports a setting, the policy evaluator (internal/security/policy.go) records status: "unknown" and excludes that rule's weight from the score denominator rather than silently counting it as pass.

4. What is the difference between accepted and verified configuration writes?

Many printers return an SNMP NoError or IPP successful-ok response even when a setting is ignored by firmware or write-only. After applying a change (internal/configmgmt/service.go), PrintMarshal performs an immediate read-back poll:

  • verified (verified: true): The read-back value matches the desired value written.
  • accepted (verified: false): The driver write succeeded without error, but the key is write-only (such as passwords/communities) or could not be confirmed on read-back.
5. Can PrintMarshal enroll and install TLS certificates on printers?

PrintMarshal implements CSR generation (RSA-2048) and certificate enrollment via its built-in encrypted root CA, EST (/.well-known/est/simpleenroll), or SCEP, and raises expiry warnings at ≤ 30 days and critical alerts at ≤ 7 days (internal/security/certs.go).

Installing an enrolled certificate onto physical printer hardware (POST /api/devices/{id}/certificates/{issuedId}/install) requires a model-specific driver implementing driver.CertificateInstaller. Without a vendor installer driver, operators download the enrolled certificate/bundle and upload it through the printer's web console.

6. Does PrintMarshal push firmware updates to physical printers?

Not without a vendor firmware driver. PrintMarshal includes a SHA-256 verified firmware repository, version-compliance rules, and campaign scheduling. Out of the box, end-to-end HTTP firmware delivery (POST /fw-sim) is wired strictly for loopback simulator targets (127.0.0.1 / localhost running pm-sim). Delivering firmware to physical printers requires implementing driver.FirmwareDriver.

7. Is PrintMarshal a print server, pull-print queue, or print accounting tool?

No. PrintMarshal manages devices, not print jobs. Print job accounting, page quotas, cost allocation, secure badge release, and pull printing are outside PrintMarshal (README.md, docs/print-provider.md, internal/printprovider/settings.go).

For small Linux sites that want host print queues to follow PrintMarshal's device inventory, PrintMarshal includes an optional, off-by-default local CUPS queue add-on (internal/printprovider/). When enabled (enabled: true), it runs in one of two modes:

  • ipp-everywhere-list: Publishes discovered IPP Everywhere / driverless URIs (ipp:// or ipps://) for workstations without changing the host.
  • cups: On a Linux host with lpadmin, lpstat, cupsenable, and cupsaccept installed, it plans (GET /api/print-provider/plan), previews (POST /api/print-provider/sync with dryRun: true by default), creates/updates, and removes (DELETE /api/print-provider/queues/{deviceId}) local CUPS queues carrying its prefix (pm- by default). On non-Linux hosts or when CUPS CLI tools are absent, it falls back to DryBackend (recording commands only). It never modifies a printer.
8. How are printer credentials and encryption keys protected?

All stored SNMP community strings, SNMPv3 passphrases, IPP credentials, and CA/CSR private keys are encrypted at rest using AES-256-GCM (internal/secrets/secrets.go) keyed by PM_SECRET_KEY (a base64-encoded 32-byte key generated via openssl rand -base64 32 or persisted at <PM_DATA_DIR>/secret.key).

Preserve PM_SECRET_KEY across restarts: if you replace PM_SECRET_KEY against an existing database, previously stored credentials cannot be decrypted. Always back up secret.key in your secrets manager alongside database backups (deploy/scripts/backup.sh).
