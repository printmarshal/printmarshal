# Spec: dashboard layout and security-posture widget (from intent.md 2026-10-31)

## Requirements
1. The dashboard is a list of widgets drawn from a fixed catalogue in the SPA. Each widget has an id, a title, a size (`sm` for a number card, `md` for a half-width card, `lg` for full width) and a minimum role. The catalogue is: the six number cards (`kpi.devices`, `kpi.online`, `kpi.alerts`, `kpi.supplies`, `kpi.stock`, `kpi.jobs`), `security.posture` (new), `fleet.health`, `alerts.recent`, `devices.attention`, `supplies.low`, `jobs.inprogress`, `activity.recent` (operator and above), `consumables.lowstock`, `consumables.reorder`.
2. A layout is an ordered list of entries `{id, hidden, collapsed}`; order in the list is order on the page. A layout that omits a catalogue widget shows it after the listed ones with its defaults; an entry whose id is not in the catalogue is ignored and dropped on the next save. A layout is therefore valid across releases that add, rename or remove widgets.
3. Every signed-in user sees the effective layout: their personal layout if they saved one, else the instance default if an administrator saved one, else the built-in default. The built-in default order is the number cards, then `security.posture` beside `alerts.recent`, then `fleet.health`, `devices.attention`, then `supplies.low`, `jobs.inprogress`, `activity.recent`, then the two consumables widgets; nothing hidden.
4. Any user with a session can save, replace and reset their personal layout. Only an administrator can save or reset the instance default. API tokens get 403 on every layout route: layouts are for people.
5. An edit mode on the dashboard, entered with a "Customise" button, lets the user hide, show, collapse, expand and move each widget up or down with buttons; every control is a real button with a label and keyboard focus. Hidden widgets are listed in a tray at the bottom with a "Show" control. "Done" saves the personal layout; "Reset" removes it; an administrator also sees "Save as default for everyone" and "Clear default". Outside edit mode the page looks as it does today, minus hidden widgets, with collapsed widgets showing only their header.
6. Hiding, collapsing or reordering never changes what data a principal receives: the dashboard payload and every widget keep today's role gates and group-scope filtering.
7. `security.posture` shows, for the devices the principal may see: average score, compliant count, non-compliant count, devices not yet assessed, and the total number of items reported as unknown across the fleet, with unknown shown in its own colour and never folded into pass. It links to the Security page. With no assessments it shows an empty state that says to run an assessment.
8. The compliance summary gains `unknown` (sum of each assessment's unknown items) and `notAssessed` (devices in scope without a latest assessment), and the Security page's summary numbers show the same two values so the dashboard and the Security page agree.
9. On a phone (one column) the order is the effective layout's order; collapse and hide still apply; edit mode works with the same buttons.
10. Deleting a user deletes that user's personal layout.

## Design
- **Web (`web/src`).** New `dashboard/catalogue.ts` (the catalogue and the built-in default), `dashboard/layout.ts` (merge effective layout = personal ?? default ?? built-in, normalise against the catalogue, move/hide/collapse helpers), `dashboard/EditBar.tsx` (edit-mode toolbar) and a `WidgetFrame` that wraps a `Card` with the per-widget edit controls. `pages/Dashboard.tsx` becomes a map over the effective layout that renders each widget by id from today's JSX, split into one component per widget in `dashboard/widgets/`. New `SecurityPosture.tsx` widget. `types.ts` gains `DashboardLayout`, `LayoutEntry` and the extended `Dashboard` payload with `security` and `layout`.
- **API (`internal/api`).** `GET /api/dashboard` adds `security` (the compliance summary over the principal's visible devices, via `LatestAssessments` with the resolved device ids) and `layout` (`{effective, personal, default}`) so the page loads in one request. New routes: `PUT /api/dashboard/layout` (own), `DELETE /api/dashboard/layout` (own), `PUT /api/dashboard/layout/default` (admin), `DELETE /api/dashboard/layout/default` (admin). Bodies are validated: known ids only after normalisation, booleans only, at most one entry per id, body under 16 KB. `authorize` denies tokens on `/api/dashboard/layout`. `deleteUser` removes the personal layout key.
- **Store.** Layouts live in the `settings` table under `dashboard.layout.default` and `dashboard.layout.user.<userID>` (JSON). One new store method `DeleteSetting(ctx, key)` on both SQLite and PostgreSQL. No migration.
- **Security.** `security.Summarize` takes the assessed set plus the count of devices in scope, and returns `Unknown` and `NotAssessed` in `ComplianceSummary`; `GET /api/compliance` passes the scoped device count.
- **UI states.** Loading skeleton unchanged; error banner unchanged; empty states per widget unchanged; new states: edit mode on/off, hidden tray empty or not, posture empty state, "saved" and "reset" confirmations as the existing toast.
- **Docs.** API reference (wiki `API-reference`) gets the four routes and the payload fields; the wiki's monitoring page gets a short "Customising the dashboard" section.

## Flagged concerns
- **Unknown is never pass.** The posture widget must show unknown as its own number, not inside the score; the score already excludes unknown items from its denominator. Reviewer: check the widget and the Security summary show the same numbers for the same device set.
- **Scope.** The posture summary must be computed over the principal's visible devices only, like every other dashboard number (audit NV-03 class of defect). Covered by a test with a scoped token.
- **Brand.** The edit controls use the existing button and icon set; no new colours. The posture widget uses the state colours for compliant, non-compliant and unknown, the same as the Security page.
- **No drag-and-drop.** Deliberately out: it needs a dependency and a pointer-only interaction. Up/down buttons give the same result and work with a keyboard. Resizing is out for the same reason.

## Out of scope
Multiple named dashboards, role-based dashboards, sharing or export, per-widget settings (filters, groups), new widgets beyond security posture, and any licensing or entitlement.
